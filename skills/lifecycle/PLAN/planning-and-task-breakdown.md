## 概述

将 SPEC.md 或需求文档分解为具体的、可验证的小任务。每个任务都应该是独立的、可测试的、可在一轮对话中完成的。

## 何时使用

- 有 SPEC.md 或需求文档后
- 用户说"帮我规划一下怎么做"
- 任务看起来很大，需要分步

## 流程

### 第一步：只读模式分析
- 读取 SPEC.md 或需求文档
- 识别所有功能点和改动点
- 标记依赖关系

### 第二步：依赖图
画出任务之间的依赖关系：
```
Task A → Task B → Task D
       ↘ Task C ↗
```

### 第三步：垂直切片
按用户可见的功能垂直切分（不要按层切分）：
- 正确： "用户注册功能"（前端+后端+数据库）
- 错误： "数据库表设计"、"API 开发"、"前端页面"

### 第四步：写任务
每个任务包含：
- 描述：一句话说明做什么
- 验收标准：1-3 条可验证条件
- 依赖：前置任务
- 预估难度：S/M/L

### 第五步：输出

写入 `tasks/plan.md`（依赖图和概览）和 `tasks/todo.md`（任务列表）：

```markdown
# 执行计划
## 依赖图
## 阶段划分

# 任务列表
## [ ] Task 1: 描述 (依赖: none, 难度: M)
  - 验收: ...
## [ ] Task 2: 描述 (依赖: Task 1, 难度: S)
  - 验收: ...
```

## 常见合理化借口

- "直接做就行了，不用分任务" — 没有分解的任务会越做越大
- "这个任务太小了不值得写" — 小任务也写一行，成本为零

## 红旗信号

- 有一个任务超过 5 个验收标准
- 无法确定任务间的依赖关系
- 任务的预估全是 L（大）

## 验证

- [ ] 每个任务有验收标准
- [ ] 依赖图不存在循环依赖
- [ ] 总任务数不超过 15 个（否则需要更高层次的抽象）
